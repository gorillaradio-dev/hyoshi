Layout & navigazione mobile

Il trainer usa TrainerHub spesso dal telefono: dal bordo campo, in palestra, mentre registra un pagamento al volo. Per questo l'UI è mobile-first — non "responsive che funzionicchia anche su mobile", ma progettata prima per il telefono e poi adattata al desktop. La differenza si vede nei layout.

I layout

LayoutQuando
TenantLayoutTutte le pagine sotto /app/{slug}/
CentralLayoutOnboarding, billing, pagine "non ancora in un tenant"
AuthLayoutLogin, register, password reset, 2FA
SettingsLayoutProfilo, password, appearance, 2FA setup

Vivono in resources/js/layouts/. Si assegnano alla pagina con il persistent layout pattern di Inertia: 

// resources/js/pages/Tenant/Student/Show.tsx
import TenantLayout from '@/layouts/tenant-layout';
import type { ReactElement } from 'react';

export default function StudentShow(props: Props) {
    // ...
}

StudentShow.layout = (page: ReactElement) => <TenantLayout>{page}</TenantLayout>;

Il vantaggio del persistent layout: navigando tra pagine che condividono lo stesso layout, il chrome (sidebar, header) non si smonta — lo state interno (es. scroll della sidebar, menu aperto) rimane.

TenantLayout nel dettaglio

File: resources/js/layouts/tenant-layout.tsx. Il layout decide al runtime se renderizzare la versione mobile o desktop in base all'hook useIsMobile(). 

export default function TenantLayout({ children, breadcrumbs = [] }: AppLayoutProps) {
    const isMobile = useIsMobile();
    const tenant = useTenant();
    const prefix = `/app/${tenant.slug}`;

    // Risolve breadcrumb relativi al prefix tenant
    const resolvedBreadcrumbs = breadcrumbs.map((item) => ({
        ...item,
        href: typeof item.href === 'string' && !item.href.startsWith('/') && item.href !== '#'
            ? `${prefix}/${item.href}`
            : item.href,
    }));

    if (isMobile) {
        return (
            <div className="flex min-h-svh flex-col bg-background">
                <TenantMobileHeader />
                <main className="flex flex-1 flex-col pb-16">{children}</main>
                <TenantBottomNav />
            </div>
        );
    }

    return (
        <AppShell variant="sidebar">
            <TenantSidebar />
            <AppContent variant="sidebar" className="overflow-x-hidden">
                <AppSidebarHeader breadcrumbs={resolvedBreadcrumbs} />
                {children}
            </AppContent>
        </AppShell>
    );
}

L'hook useIsMobile() in resources/js/hooks/use-mobile.ts legge un media query breakpoint. La scelta tra mobile/desktop avviene al primo render e si aggiorna al resize.

Chrome mobile

Due componenti compongono il chrome mobile:

  • TenantMobileHeader (resources/js/components/tenant-mobile-header.tsx) — header sticky in alto con logo, nome tenant, menu utente. Compatto, alto solo lo stretto necessario.
  • TenantBottomNav (resources/js/components/tenant-bottom-nav.tsx) — bottom nav fissa con le 3-4 sezioni principali (Dashboard, Allievi, Gruppi, …). Pattern iOS/Android nativo. Pulsante centrale o destro per l'azione primaria.

Il pb-16 sul <main> riserva lo spazio per la bottom nav in modo che il contenuto non vada sotto.

Chrome desktop

  • AppShell + TenantSidebar — sidebar laterale fissa con navigazione completa, raggruppata per sezione. Apertura/chiusura persistita via cookie (sidebar_state è una shared prop Inertia).
  • AppSidebarHeader — header con breadcrumb risolti tenant-aware. Il layout normalizza i breadcrumb relativi nel prefix /app/{slug}/.
  • AppContent — area scrollabile principale.

CentralLayout

File: resources/js/layouts/central-layout.tsx. Layout più semplice per pagine non-tenant: niente sidebar, header minimale con logo e profilo. Usato per onboarding e future pagine di billing.

Filosofia "responsive"

  • Mobile è il default: scrivi prima la versione mobile, poi aggiungi modificatori md:/lg: Tailwind per il desktop.
  • Touch target ≥ 44px: bottoni e link cliccabili devono essere comodi col dito. shadcn Button con dimensione default rispetta questo.
  • Niente hover-only: ogni azione raggiungibile via hover su desktop deve avere un fallback tap-friendly su mobile (long press, menu kebab, ecc.).
  • Test mobile reale: docs/mobile-testing.md spiega come esporre il dev server in LAN e testare dal telefono.

Prima di committare una nuova pagina, aprila sul tuo telefono. Se non è comoda da usare in piedi con una mano, va ripensata — non semplicemente "lasciamola così, tanto funziona".
