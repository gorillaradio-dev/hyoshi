Convenzioni frontend

Le regole frontend di TrainerHub sono non negoziabili: derivano da esperienze costose. Niente "ma in questo caso fa eccezione". Se la regola sembra di troppo, prima cerca un modo per rispettarla — solo dopo discutila con il team.

La fonte di verità di queste convenzioni è CLAUDE.md nella radice del repo.

TypeScript: zero compromessi

  • Mai any. Se non sai il tipo, usa unknown e narrowla.
  • Mai ! (non-null assertion). Risolvi con guard espliciti.
  • Mai as unsafe. Usa generics, type guard, helper tipizzati.
  • Se TypeScript si lamenta, risolvi alla radice: hook custom che ritorna il tipo giusto, predicato di type guard, props meglio definite. Non zittire il compilatore.

Esempio cattivo (proibito):

// ❌ NO
const student = props.student as Student;
const phone = student.phoneContact!.phone;

Esempio buono:

// ✅ OK
interface ShowProps { student: Student; }

export default function Show({ student }: ShowProps) {
    const phone = student.phoneContact?.phone ?? student.phone ?? '—';
    // ...
}

Path imports: mai relativi profondi

Usa il path alias @/ (configurato in tsconfig.json → resources/js/). I ../../ sono vietati. 

// ❌ NO
import { useTenant } from '../../hooks/use-tenant';

// ✅ OK
import { useTenant } from '@/hooks/use-tenant';

UI: shadcn obbligatorio

Tutta la UI parte da shadcn/ui. Prima di creare un componente custom, cerca su ui.shadcn.com: se esiste già, usa quello. Si aggiungono al progetto con la CLI shadcn (vivono in resources/js/components/ui/).

  • Mai re-implementare Button, Input, Select, Dialog, Sheet, Tabs, Card, Table, … shadcn ce li ha.
  • I primitivi shadcn sono copiati nel progetto, non importati come libreria: puoi modificarli liberamente per il tuo design.
  • Quando shadcn non ha quello che ti serve, puoi comporre i primitivi esistenti. Solo se proprio nulla esiste, scrivi un componente custom — ma documenta perché.

Form: useForm sempre

Per ogni form usa useForm di Inertia. Mai useState + fetch manuale: perderesti integrazione con validazione, errori, progress, ed esporresti CSRF vulnerabilities. 

// ✅ OK
const form = useForm({ name: '', email: '' });
form.post('/users', { onSuccess: () => form.reset() });

// ❌ NO
const [name, setName] = useState('');
fetch('/users', { method: 'POST', body: JSON.stringify({ name }) });

Props: sempre interface esplicita

Ogni componente espone un'interface per le sue props, idealmente derivata dai tipi di dominio in resources/js/types/. 

// ✅ OK
interface StudentCardProps {
    student: Student;
    onEdit?: (s: Student) => void;
}

export function StudentCard({ student, onEdit }: StudentCardProps) {
    // ...
}

Layout: persistent layout pattern

Ogni pagina assegna il layout con il static layout property, non con un wrapping JSX: 

// ✅ OK — layout persistente
StudentShow.layout = (page: ReactElement) => <TenantLayout>{page}</TenantLayout>;

// ❌ NO — layout dentro il return
return <TenantLayout>...</TenantLayout>;

Tenant: useTenant()

Non destrutturare usePage().props.tenant a mano: usa l'hook useTenant() che lancia se il tenant non c'è. Previene bug subdoli sulle route centrali.

Mobile-first

Vedi Layout & navigazione mobile. Le classi Tailwind di default sono mobile; i modificatori md: e lg: aggiungono il comportamento desktop: 

// ✅ OK — mobile-first
<div className="flex flex-col md:flex-row">...</div>

// ❌ NO — desktop-first ribaltato
<div className="flex flex-row max-md:flex-col">...</div>

Lingua

  • Codice, commenti, naming: inglese.
  • UI labels e messaggi utente: italiano.
  • Documentazione interna: italiano (questa).

Lint e formattazione

Comandi essenziali:

npm run lint       # ESLint con --fix (autofixa import order, ecc.)
npm run lint:check # ESLint senza fix (usato in CI)
npm run format     # Prettier --write
npm run format:check
npm run types:check # tsc --noEmit (verifica solo tipi, no build)

Il workflow CI lint.yml gira npm run lint ed npm run format in --check. Se fallisce, gira localmente npm run lint && npm run format prima del prossimo push.

Review frontend

Dopo ogni blocco significativo di lavoro UI, esegui la checklist della skill frontend-review (Claude Code). Punti chiave:

  • shadcn-first verificato (nessun componente custom riproducibile con shadcn).
  • Inertia-first verificato (nessun fetch manuale, useForm dove serve).
  • Tailwind-first (no inline styles, no CSS modules non motivati).
  • Mobile-first verificato (testato a 375px di larghezza minimo).
  • Nessun any/!/as introdotto.
  • Nessun path relativo profondo.
