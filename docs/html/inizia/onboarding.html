Onboarding sviluppatore

Sei nuovo in TrainerHub? Questa pagina è un percorso lineare per orientarti nel codebase nell'ordine giusto: prima i concetti, poi i layer, infine i punti di attenzione. Non leggere a caso — il progetto è multi-tenant e capire quello per primo evita di fraintendere il resto.

Prerequisiti

  • PHP 8.3 (preferito) o 8.4 — il deploy gira su 8.4, la CI testa su 8.4 e 8.5.
  • Composer 2.x.
  • Node 22 + npm (i workflow CI usano Node 22).
  • MySQL 8 locale: utente root, no password, database trainerhub.
  • Git con accesso a gorillaradio-dev/hyoshi.

Per la procedura passo-passo di setup vedi Setup locale. Qui ci concentriamo su come orientarsi nel codice, non su come installarlo.

Il percorso consigliato

L'ordine conta. Le sezioni più in basso danno per scontato che hai capito quelle in alto.

  1. Cosa fa TrainerHub. Parti dalla Panoramica: gestionale multi-tenant per personal trainer; ogni trainer gestisce allievi, gruppi, quote mensili e iscrizioni dentro il suo "spazio" isolato.
  2. Multi-tenancy single-database. È la cosa da capire bene prima di tutto il resto. Vedi Multi-tenancy: tutti i tenant condividono lo stesso DB, ma un global scope su tenant_id impedisce a un tenant di vedere dati di un altro.
  3. Architettura applicativa. Vista d'insieme per i layer (HTTP → Dominio → Dati, frontend React via Inertia), poi Modello dati per le entità reali.
  4. Il dominio dei pagamenti. È la parte più sottile del progetto. Quote mensili e Iscrizioni spiegano i tre service tariffe (FeeCalculationService, MonthlyFeeService, EnrollmentFeeService). Gli importi sono interi in centesimi: ricordatelo prima di scrivere qualunque calcolo.
  5. HTTP e frontend. Routing + Controller per capire come arriva una richiesta; poi Architettura Inertia per capire come la risposta diventa una pagina React.
  6. Convenzioni. Convenzioni frontend e CLAUDE.md nella radice del repo: regole non negoziabili (UUID, centesimi, mai any in TS, shadcn obbligatorio, mobile-first).
  7. Deploy e branch strategy. Branch strategy + Deploy: main è il trunk e deploya all'ambiente staging via GitHub Actions.

Concetti chiave (da sapere a memoria)

  • Multi-tenancy single-database. Un solo database condiviso, colonna tenant_id su ogni tabella tenant-scoped, isolamento gestito dal trait BelongsToTenant di stancl/tenancy.
  • Controller thin + Service. I controller validano (FormRequest), applicano le Policy e delegano la business logic ai service in app/Services.
  • UUID + centesimi. Chiavi primarie UUID via trait HasUuids; importi monetari come integer in centesimi (es. 5000 = €50,00).
  • Backed enum PHP. StudentStatus, PaymentMethod, DocumentType, DocumentStatus: stati non validi impossibili a livello di tipo.
  • Inertia, non REST. Il backend non espone un'API JSON: risponde con il nome di un componente React e le sue props; il frontend lo monta via resolvePageComponent.
  • Mobile-first. Il trainer usa spesso il telefono — ogni pagina nuova va pensata mobile e poi adattata desktop, non viceversa.

Quando metti mano al codice

Per ogni cambiamento, queste sono le abitudini che ti aspettiamo:

  • Una modifica tenant-scoped richiede sempre il trait BelongsToTenant sul modello e una Policy sul controller.
  • Mai any / ! / as non sicuri in TypeScript. Se TS si lamenta, risolvi alla radice con tipi corretti, hook custom o guard.
  • Mai creare un componente UI a mano: cerca prima su shadcn/ui e usa quello.
  • Per ogni feature scrivi almeno un feature test (Pest) che verifichi l'isolamento tenant: tenant A non deve vedere/toccare dati di tenant B.
  • Vai sempre via PR verso main (default branch). Se il tuo lavoro deve essere mergiato e chiudere un'issue, usa Closes #N nel body.
