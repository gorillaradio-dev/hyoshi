Deploy & CI/CD

TrainerHub usa GitHub Actions per CI e CD. La regola d'oro: ogni push a main deploya automaticamente all'ambiente staging (hyoshi.gorillaradio.dev). Niente deploy manuali, niente push diretti al server.

Deploy a staging

File: .github/workflows/deploy.yml. Usa appleboy/ssh-action per eseguire uno script SSH sul server. Job singolo, no sudo (i permessi sono pre-impostati, vedi memory). 

on:
  push:
    branches: [main]
  workflow_dispatch:

jobs:
  deploy-staging:
    if: github.ref_name == 'main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.HOST }}
          username: ${{ secrets.USERNAME }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          port: ${{ secrets.PORT }}
          script: |
            set -e
            cd /var/www/hyoshi-staging
            git remote set-url origin git@github-hyoshi:gorillaradio-dev/hyoshi.git
            rm -rf public/storage
            git pull origin main
            composer install --no-dev --optimize-autoloader --no-interaction
            php artisan migrate --force
            php artisan optimize:clear
            php artisan storage:link

            npm ci
            # Build con retry 3x (Wayfinder può fallire la prima volta)
            for i in 1 2 3; do
              if npm run build; then break; fi
              [ $i -eq 3 ] && exit 1
              sleep 60
            done

GitHub secrets richiesti

  • HOST — hostname del server
  • PORT — porta SSH
  • USERNAME — utente di deploy (deploy)
  • SSH_PRIVATE_KEY — chiave privata corrispondente alla deploy key registrata su GitHub
  • DOCS_SYNC_TOKEN — PAT fine-grained Contents:Write su gorillaradio-dev/go-docs (solo per sync-docs.yml)

Test e lint in CI

I workflow tests.yml e lint.yml girano su push e PR a main e production. Setup matrix PHP 8.4 + 8.5, Node 22. Una build rossa blocca implicitamente il merge (la review umana + le check fan il loro lavoro). 

# tests.yml — sequenza essenziale
- Setup PHP (8.4 e 8.5) con shivammathur/setup-php
- Setup Node 22
- npm i + composer install
- cp .env.example .env + php artisan key:generate
- npm run build
- ./vendor/bin/pest

# lint.yml
- composer lint   (Pint)
- npm run format  (Prettier)
- npm run lint    (ESLint)

Sync docs verso portale

sync-docs.yml mirror-a docs/html/ verso il subfolder hyoshi/ del repo gorillaradio-dev/go-docs. Da lì, un Cloudflare Worker serve docs.gorillaradio.dev — quindi ogni push docs è di fatto un deploy del portale.

  • Trigger limitato a cambi in docs/html/**.
  • Concurrency group sync-docs-${{ github.ref }}: una push doppia non racing.
  • Usa DOCS_SYNC_TOKEN, non GITHUB_TOKEN (scope limitato al repo destinazione).

Rollback

Non esiste un meccanismo automatico. Per ora:

  1. Identifica il commit ultimo "buono" su main.
  2. Revert sul ramo o crea una PR di revert: git revert <sha> + PR.
  3. Mergia la PR di revert su main → il workflow deploy ridepiega.

Per emergenze, è possibile fare push diretto su main dell'utente con i permessi (no PR), ma è da evitare salvo casi davvero urgenti.

Monitoraggio CI

Comandi utili dal terminale:

gh run list --branch main --limit 5
gh run view <run-id>
gh run view <run-id> --log-failed
gh workflow run deploy.yml --ref main   # trigger manuale

Mai aggiungere sudo al deploy script. La filosofia è: il server è pre-configurato una volta, l'utente deploy ha solo i permessi che servono, il workflow non può escalare. Se serve un nuovo permesso, lo si imposta a mano sul server (e si documenta).
