Multi-tenancy

TrainerHub è multi-tenant: ogni trainer (palestra) ha il suo spazio isolato dentro lo stesso database condiviso. L'isolamento è garantito da una combinazione di tre meccanismi che lavorano in sequenza: identificazione del tenant dal path, inizializzazione del contesto, e global scope automatico sulle query.

Approccio: single-database con discriminante

Tutti i tenant condividono un solo database MySQL. Ogni tabella tenant-scoped porta una colonna tenant_id che identifica il proprietario delle righe. La libreria stancl/tenancy v3 gestisce identificazione, scoping e ciclo di vita.

La scelta single-database è esplicita: DatabaseTenancyBootstrapper è disabilitata in config/tenancy.php. Restano attivi i bootstrapper per cache, filesystem e queue, che restano "tenant-aware" senza dover spostare i dati su database separati. 

// config/tenancy.php
'bootstrappers' => [
    // DatabaseTenancyBootstrapper disabilitato — usiamo single-database mode
    // Stancl\Tenancy\Bootstrappers\DatabaseTenancyBootstrapper::class,
    Stancl\Tenancy\Bootstrappers\CacheTenancyBootstrapper::class,
    Stancl\Tenancy\Bootstrappers\FilesystemTenancyBootstrapper::class,
    Stancl\Tenancy\Bootstrappers\QueueTenancyBootstrapper::class,
],

stancl/tenancy supporta anche multi-database. Il vantaggio dell'approccio single-database è la semplicità operativa (una sola migrazione, un solo backup, una sola connessione). Se un tenant cresce molto, è possibile migrarlo su un DB dedicato senza riscrivere il codice applicativo.

Identificazione: path-based

Le route tenant vivono sotto il prefisso app/{tenant}. Il middleware Stancl\Tenancy\Middleware\InitializeTenancyByPath legge il parametro {tenant}, cerca il tenant corrispondente e inizializza il contesto.

La chiave del tenant è lo slug, non l'ID: il modello App\Models\Tenant override getTenantKeyName() per ritornare 'slug'. Quindi gli URL sono leggibili: /app/palestra-rossi/students invece di /app/9f3a-…-uuid/students. 

// app/Models/Tenant.php
class Tenant extends BaseTenant
{
    public function getTenantKeyName(): string
    {
        return 'slug';
    }
}

Stack middleware delle route tenant

L'ordine dei middleware è critico. Da routes/tenant.php: 

Route::middleware(['web', 'auth', InitializeTenancyByPath::class, 'tenant.access'])
    ->prefix('app/{tenant}')
    ->group(function () {
        // ...route tenant
    });

  1. web — sessione, CSRF, cookies, HandleInertiaRequests.
  2. auth — l'utente deve essere loggato prima di passare oltre.
  3. InitializeTenancyByPath — risolve {tenant} dallo slug e popola la facade tenant(). Se non trova nulla, lancia TenantCouldNotBeIdentifiedByPathException → mappata a 404 da bootstrap/app.php.
  4. tenant.access — alias del custom middleware EnsureTenantAccess: verifica che l'utente autenticato sia il proprietario del tenant; altrimenti abort(403).
// app/Http/Middleware/EnsureTenantAccess.php
public function handle(Request $request, Closure $next)
{
    $tenant = tenant();

    if (! $tenant || $tenant->owner_id !== $request->user()->id) {
        abort(403);
    }

    return $next($request);
}

Oggi solo l'owner del tenant può accedere. Quando aggiungeremo team members o ruoli, l'unico file da estendere è EnsureTenantAccess — il resto della pipeline resta uguale.

Global scope automatico

Una volta inizializzato il tenant, ogni modello tenant-scoped applica automaticamente un filtro WHERE tenant_id = ? a tutte le query e assegna tenant_id in fase di creazione. Il merito è del trait Stancl\Tenancy\Database\Concerns\BelongsToTenant.

I modelli che lo usano:

ModelloTrait
StudentBelongsToTenant
GroupBelongsToTenant
GroupStudentBelongsToTenant
MonthlyFeeBelongsToTenant
EnrollmentFeeBelongsToTenant
PaymentBelongsToTenant
DocumentBelongsToTenant
EmergencyContactBelongsToTenant

Modelli centrali (User, Tenant) non usano il trait: vivono fuori dal contesto tenant. Anche una migrazione che aggiunge nuove tabelle tenant-scoped deve includere $table->uuid('tenant_id')->index().

Garanzie e responsabilità

Il global scope ti protegge da letture indesiderate, ma non da tutto.

  • Cosa il trait fa per te. Filtra automaticamente le query Model::all(), Model::find($id), $tenant->students: un tenant non vede MAI righe di altri tenant. Alla creazione, popola tenant_id con quello corrente.
  • Cosa tu devi fare. Aggiungere una Policy a ogni modello tenant-scoped (vedi Policy & authorization): il global scope blocca le query, ma le Policy aggiungono un secondo livello di controllo sull'azione richiesta. Per file path costruiti dall'utente, prefissa sempre con tenants/{tenant_id}/.
  • Test obbligatorio. Per ogni feature tenant scrivi un Pest test che dimostri l'isolamento: crea tenant A e B, esegui l'azione come A, verifica che B non veda né tocchi nulla.

Frontend: il tenant condiviso via Inertia

Il middleware HandleInertiaRequests condivide il tenant corrente con il frontend, in modo che ogni pagina React abbia accesso a name/slug. Lato client, l'hook useTenant() in resources/js/hooks/use-tenant.ts lo legge dalle shared props di Inertia.

MAI accedere a dati tenant senza passare dal global scope. Non usare DB::table('students') raw o disabilitare lo scope con withoutGlobalScopes() a meno che tu non stia facendo manutenzione cross-tenant esplicita (e in quel caso documenta perché).
