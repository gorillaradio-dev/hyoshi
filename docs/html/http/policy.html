Policy & authorization

L'autorizzazione in TrainerHub funziona a tre livelli: middleware tenant.access (ownership tenant), global scope Eloquent (filtro dati), e Policy per risorsa (permesso sull'azione). Le Policy sono il livello applicativo: il controller chiama $this->authorize(...) prima di ogni azione, e Laravel risolve la Policy giusta in base al modello.

Le tre difese sono complementari, non ridondanti: il middleware blocca accessi a tenant non tuoi, lo scope impedisce di vedere righe altrui anche per errore di codice, e la Policy decide se quella specifica azione è permessa.

Esempio: StudentPolicy

File: app/Policies/StudentPolicy.php. Tutte le azioni oggi ritornano true perché l'unico utente possibile è l'owner del tenant (già verificato dal middleware tenant.access). Quando aggiungeremo ruoli (admin, collaboratore, sola lettura), la logica vivrà qui. 

namespace App\Policies;

use App\Models\Student;
use App\Models\User;

class StudentPolicy
{
    public function viewAny(User $user): bool
    {
        return true; // tenant.access middleware già verifica accesso
    }

    public function view(User $user, Student $student): bool
    {
        return true;
    }

    public function create(User $user): bool
    {
        return true;
    }

    public function update(User $user, Student $student): bool
    {
        return true;
    }

    public function delete(User $user, Student $student): bool
    {
        return true;
    }
}

L'apparente "no-op" delle Policy è intenzionale: la struttura è già pronta per ricevere logica di ruolo. Quando arriverà, non serve cambiare i controller — basta editare la Policy.

Come si usano nei controller

In ogni metodo del controller, la prima riga è la chiamata a authorize. Laravel risolve la Policy in base al modello passato come secondo argomento. 

// Sull'intero modello (per viewAny / create):
$this->authorize('viewAny', Student::class);
$this->authorize('create', Student::class);

// Su un'istanza (per view / update / delete):
$this->authorize('view', $student);
$this->authorize('update', $student);
$this->authorize('delete', $student);

Se la Policy ritorna false, Laravel risponde con 403 Forbidden automaticamente. Niente if espliciti, niente check ridondanti.

Registrazione automatica

Laravel 11+ scopre le Policy automaticamente in base alla convenzione di naming: App\Models\Student → App\Policies\StudentPolicy. Non serve mappa manuale in AuthServiceProvider (assente in questo progetto).

Se una Policy con il nome convenzionale non esiste, authorize lancia AuthorizationException al primo accesso. Quindi: aggiungere una Policy ogni volta che aggiungi un modello tenant-scoped è obbligatorio.

Lato frontend

Inertia non espone Policy al client come fa Laravel-Sanctum o Spatie/permission. Se serve una verifica lato UI (es. nascondere il bottone "elimina"), passa il flag come prop Inertia calcolato lato controller: 

return Inertia::render('Tenant/Student/Show', [
    'student' => $student,
    'can' => [
        'update' => $request->user()->can('update', $student),
        'delete' => $request->user()->can('delete', $student),
    ],
]);

Esempio: aggiungere ruolo "sola lettura"

Scenario futuro: un collaboratore del trainer può vedere gli studenti ma non modificarli. 

// 1. Aggiungi una colonna users.role oppure una tabella tenant_user pivot

// 2. Estendi tenant.access per ammettere anche i collaboratori
class EnsureTenantAccess
{
    public function handle(Request $request, Closure $next)
    {
        $tenant = tenant();
        $user = $request->user();

        $isOwner = $tenant?->owner_id === $user->id;
        $isMember = $tenant?->members()->where('user_id', $user->id)->exists();

        if (! $tenant || (! $isOwner && ! $isMember)) {
            abort(403);
        }

        return $next($request);
    }
}

// 3. Restringi le Policy per ruolo
class StudentPolicy
{
    public function update(User $user, Student $student): bool
    {
        return tenant()->owner_id === $user->id
            || $user->tenantRole(tenant())->canEdit();
    }
}

Tre file toccati, controller invariati. Questo è il vantaggio dell'aver tenuto le Policy pulite anche quando "non servono".
