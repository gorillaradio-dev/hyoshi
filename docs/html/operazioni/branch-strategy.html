Branch strategy

TrainerHub adotta il modello a singolo trunk + branch di release: main è il branch attivo dove confluisce tutto il lavoro e da cui parte il deploy a staging; production è il branch dedicato al futuro deploy di produzione. Le PR vanno sempre verso main.

I branch

BranchRuoloDeploy
mainDefault GitHub. Trunk attivo dove arrivano le PR.Auto-deploy a hyoshi-staging (vedi Deploy)
productionDedicato al deploy di produzione.Nessun deploy attivo (server prod non ancora esistente)
stagingLegacy congelato. Da eliminare dopo periodo di osservazione (issue hyoshi#15)—

Perché questo modello

Storicamente le PR venivano mergiate in staging perché lì viveva il deploy automatico. Conseguenza fastidiosa: i closing keywords (Closes #N nelle PR) non chiudevano le issue, perché GitHub li onora solo sul default branch.

Il 2026-05-27 abbiamo realineato: main diventa il trunk attivo (e default branch — lo era già), production nasce per il futuro deploy prod, staging resta congelato. Vedi PR hyoshi#14.

Workflow di una PR

  1. Branch dal trunk. Partendo da main aggiornato: 
    git checkout main
git pull
git checkout -b feature/<descrizione-breve>
  2. Lavora a commit piccoli e tematici. Conventional commits consigliato (feat:, fix:, refactor:, docs:, chore:, test:).
  3. Push e PR verso main. Nel body della PR usa Closes #N per le issue chiuse — ora funziona.
  4. CI verde obbligatoria. tests.yml + lint.yml devono passare.
  5. Review (umana, e/o automatica via claude-code-review.yml).
  6. Merge in main → deploy.yml deploya a staging automaticamente.

Naming dei branch

Convenzioni convenzionali (non automatizzate ma seguite):

PrefissoUso
feature/Nuove funzionalità
fix/Bug fix
refactor/Cambi che non modificano il comportamento
chore/Manutenzione (deps, config, tooling)
docs/Solo documentazione
test/Solo test (aggiunte, refactor copertura)

Regole git non negoziabili

  • Mai rebase per integrare upstream. Usa git merge origin/main per rinfrescare il tuo feature branch. Niente force-push, niente conflitti per-commit dolorosi.
  • Mai push diretto a main (salvo emergenze concordate). Sempre PR.
  • Squash o merge commit? Default merge commit: il merge della PR genera un commit di merge con riferimento alla PR. Squash solo per PR molto piccole e atomiche.
  • Body PR descrittivo. "Cosa cambia e perché", non solo "what". Per cambi non banali, includi una sezione "Test plan" o "Punti di attenzione".

Hotfix in staging (futuro: anche in production)

Quando arriverà un server di produzione, un hotfix urgente seguirà:

  1. Branch da production: git checkout -b hotfix/<...> production
  2. PR verso production (NOT main), CI verde, merge.
  3. Deploy automatico a prod (workflow da configurare).
  4. Mergia production in main per non perdere l'hotfix sul trunk.

Per ora, ogni cambio passa da main e va in staging.

Closing keywords

Nel body della PR puoi scrivere: 

Closes #42
Fixes #15, #16
Resolves #99

Al merge in main (il default branch), GitHub chiude automaticamente quelle issue. Questo era il problema originale del modello precedente e ora è risolto.

Per i cloni locali del team: dopo il realignment del 2026-05-27, fare git fetch && git checkout main && git pull. Worktree o branch locali che tracciavano staging possono essere eliminati.
