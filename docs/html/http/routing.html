Routing tenant vs central

Le route di TrainerHub sono divise per contesto: centrali (vivono fuori dal contesto tenant), tenant (vivono dentro un tenant identificato dal path), settings utente, e auth Fortify. Ogni file di route ha un middleware stack diverso e responsabilità diverse — capire la divisione è il primo passo per non sbagliare dove mettere una nuova rotta.

Le file di route

FileContestoMiddleware base
routes/web.phpCentral (welcome, dashboard redirect, onboarding)web + auth+verified per zone protette
routes/tenant.phpTenant (tutto ciò che vive dentro un tenant)web, auth, InitializeTenancyByPath, tenant.access
routes/settings.phpSettings utente (profilo, password, 2FA)auth (alcune verified + throttle)
routes/auth.phpAuth Fortify (login/register/2FA)Auto-registrate da Fortify
routes/console.phpComandi Artisan custom—

Il caricamento è fatto in bootstrap/app.php: web.php è la entry principale e include settings.php; tenant.php viene caricato nello stesso step via then callback.

Route centrali (routes/web.php)

Sono le route accessibili senza un tenant identificato. La logica chiave: dopo il login, l'utente viene reindirizzato al tenant corrente o all'onboarding. 

Route::middleware(['auth', 'verified'])->group(function () {
    Route::get('dashboard', function () {
        $user = auth()->user();
        $tenant = $user->currentTenant ?? $user->tenants()->first();

        if ($tenant) {
            if ($user->current_tenant_id !== $tenant->id) {
                $user->update(['current_tenant_id' => $tenant->id]);
            }
            return redirect()->route('tenant.dashboard', $tenant->slug);
        }

        return redirect()->route('onboarding.create');
    })->name('dashboard');

    Route::get('/onboarding', [OnboardingController::class, 'create'])->name('onboarding.create');
    Route::post('/onboarding', [OnboardingController::class, 'store'])->name('onboarding.store');
});

Route tenant (routes/tenant.php)

Tutte sotto il prefisso app/{tenant}. Lo stack middleware è in ['web', 'auth', InitializeTenancyByPath::class, 'tenant.access'] — vedi Multi-tenancy per il dettaglio.

Settings utente (routes/settings.php)

Profilo, password e 2FA — gestiti da controller in app/Http/Controllers/Settings/. Sono utente-scoped, non tenant-scoped: stesso utente, indipendentemente dal tenant corrente. 

GET   settings/profile          profile.edit
PATCH settings/profile          profile.update
DELETE settings/profile         profile.destroy
GET   settings/password         user-password.edit
PUT   settings/password         user-password.update   (throttle:6,1)
GET   settings/appearance       appearance.edit
GET   settings/two-factor       two-factor.show

Auth (routes/auth.php)

Le route di autenticazione sono registrate automaticamente da Laravel Fortify in base ai features abilitati in config/fortify.php: login, registrazione, password reset, email verification, 2FA. Non vivono in un file custom — non aggiungerle a mano.

Convenzioni naming

  • Tenant route names: sempre tenant.* (es. tenant.students.index, tenant.students.payments.monthly).
  • Central route names: dashboard, onboarding.*, profile.*, two-factor.* senza prefisso.
  • Route model binding: implicit ({student} → App\Models\Student); il global scope tenant rende il binding automaticamente tenant-safe.

Lato frontend, le route sono generate via Laravel Wayfinder: il plugin Vite produce un client TypeScript tipizzato in resources/js/routes/ e resources/js/actions/. Non importare URL come stringhe nei componenti React — usa l'helper generato.
