Testing

TrainerHub usa Pest 4 (sopra PHPUnit) per i test. La suite gira ad ogni push e PR via tests.yml. Ci sono due tipi di test: Feature (controller end-to-end, isolamento tenant) e Unit (service di dominio puri).

Comandi essenziali

composer test                # lint:check + suite Pest completa
./vendor/bin/pest            # solo suite
./vendor/bin/pest --filter "registra pagamento"
./vendor/bin/pest tests/Feature/Tenant/PaymentEdgeCasesTest.php
./vendor/bin/pest --parallel
composer ci:check            # tutto ciò che gira in CI (lint, types, test)

Struttura

tests/
├── Pest.php                          — bootstrap Pest (extend, expect, dataset)
├── TestCase.php                      — base class (estende Laravel TestCase)
├── Feature/

Pest.php

Tutti i test ricevono automaticamente RefreshDatabase (DB pulito tra un test e l'altro): 

pest()->extend(Tests\TestCase::class)
    ->use(Illuminate\Foundation\Testing\RefreshDatabase::class)
    ->in('Feature', 'Unit/Services');

Test tenant: il pattern standard

Per ogni test di feature tenant, il setup tipico è: 

beforeEach(function () {
    $this->user = User::factory()->create();
    $this->tenant = Tenant::factory()->create(['owner_id' => $this->user->id]);
    $this->user->update(['current_tenant_id' => $this->tenant->id]);
    $this->actingAs($this->user);

    // Inizializza tenancy per i test
    tenancy()->initialize($this->tenant);
});

afterEach(function () {
    tenancy()->end();
});

tenancy()->initialize(...) attiva il contesto tenant per il test, così il global scope BelongsToTenant filtra le query con il tenant giusto. tenancy()->end() lo chiude per non sporcare il test successivo.

Assertion Inertia

Pest ha helper specifici per le risposte Inertia: 

$response = $this->get("/app/{$this->tenant->slug}/students?status=all");

$response->assertOk();
$response->assertInertia(fn ($page) => $page
    ->component('Tenant/Student/Index')
    ->has('students', 3)
);

Categorie obbligatorie per ogni feature

Dalla regola di progetto (CLAUDE.md): per ogni nuova feature, copri almeno queste categorie di test:

1. Validation tests

Submit form con campi mancanti, formati non validi, valori fuori range, valori al limite + 1. Usa i dataset Pest per più payload invalidi senza copia-incolla: 

test('rifiuta payload invalido', function (array $payload, string $field) {
    $response = $this->post("/app/{$this->tenant->slug}/students", $payload);
    $response->assertSessionHasErrors($field);
})->with([
    'no first name' => [['last_name' => 'Rossi'], 'first_name'],
    'invalid email' => [['first_name' => 'Mario', 'last_name' => 'R.', 'email' => 'foo'], 'email'],
    'date in futuro'=> [['first_name' => 'M', 'last_name' => 'R', 'date_of_birth' => '2099-01-01'], 'date_of_birth'],
]);

2. Authorization tests

Verifica che un tenant non veda né tocchi dati di un altro tenant. Esempio canonico: 

test('tenant A non vede studenti di tenant B', function () {
    // Setup tenant A (dal beforeEach)
    Student::factory()->count(2)->create();   // appartengono ad A

    // Crea tenant B con un altro studente
    tenancy()->end();
    $userB = User::factory()->create();
    $tenantB = Tenant::factory()->create(['owner_id' => $userB->id]);
    tenancy()->initialize($tenantB);
    $studentB = Student::factory()->create(['first_name' => 'X-tenant']);
    tenancy()->end();

    // Torna su tenant A
    tenancy()->initialize($this->tenant);

    $response = $this->get("/app/{$this->tenant->slug}/students?status=all");

    $response->assertInertia(fn ($page) => $page
        ->has('students.data', 2)
        ->where('students.data.0.first_name', fn ($n) => $n !== 'X-tenant')
    );
});

Test anche: accesso non autenticato a route protette (assertRedirect('/login')), accesso a tenant non posseduto (assertForbidden()).

3. Business rule enforcement

Se la user story dice "X è obbligatorio" o "prevenire Y", scrivi un test che dimostra che il vincolo è applicato lato backend, non solo come warning UI.

4. Destructive action safeguards

Per ogni delete/disable/cancel: cosa succede se elimini l'ultimo elemento? Esempio: il tenant prova a rimuovere l'ultimo gruppo di un allievo che ha monthly_fee_override = null → FeeCalculationService::getEffectiveRate ritorna null, e l'app deve gestire bene questo stato (non crashare al prossimo calcolo del saldo).

Factory per ogni modello

Ogni modello ha una factory in database/factories/: UserFactory, TenantFactory, StudentFactory, GroupFactory, PaymentFactory, MonthlyFeeFactory, EnrollmentFeeFactory, ecc. Quando aggiungi un modello nuovo, aggiungi la factory nello stesso PR.

Test unit dei service

Per la logica pura (calcoli, edge case puramente algoritmici) usa tests/Unit/Services/. Sono i test più veloci e i più mirati: 

// tests/Unit/Services/FeeCalculationServiceTest.php
test('priorità override sui gruppi', function () {
    $student = Student::factory()->create(['monthly_fee_override' => 7000]);
    $group = Group::factory()->create(['monthly_fee_amount' => 5000]);
    $student->groups()->attach($group);

    $rate = app(FeeCalculationService::class)->getEffectiveRate($student);

    expect($rate)->toBe(7000);   // override vince
});

CI locale prima del push

Prima di pushare, gira la stessa pipeline della CI: 

composer ci:check

Fa:

  • npm run lint:check
  • npm run format:check
  • npm run types:check (TypeScript)
  • composer test (Pint + Pest)

Una PR senza test sufficienti per le 4 categorie (validation, authz, business rules, destructive) non è completa. La review può chiedere di aggiungere coverage prima del merge.
